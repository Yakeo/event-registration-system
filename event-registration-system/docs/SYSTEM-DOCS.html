System Documentation

Event Registration System

A web-based system for creating events and allowing participants to register online, built on the MVC pattern with Node.js, Express.js, Sequelize and EJS over MySQL or PostgreSQL.

2. Entity Relationship Diagram (ERD)

Source: docs/ERD.svg · raster copy docs/ERD.png · crow’s foot notation

2.1 Relationship notation

[EVENTS] 1 ──── 0..* [REGISTRATIONS] 0..* ──── 1 [USERS]

• One EVENT has zero or many REGISTRATIONS; each REGISTRATION is for exactly one EVENT.
• One USER has zero or many REGISTRATIONS; each REGISTRATION belongs to exactly one USER.
• REGISTRATIONS is the associative entity that resolves the many-to-many
  relationship between participants and events.

2.2 Data dictionary

USERS

FieldTypeKey / constraintDescription
user_idINT, auto incrementPKSurrogate primary key
full_nameVARCHAR(120)NOT NULLComplete name of the user
emailVARCHAR(160)UNIQUE, NOT NULLLogin name; also the duplicate-registration key

roleENUM(admin, participant)default participantAccess level of the account

EVENTS

FieldTypeKey / constraintDescription
event_idINT, auto incrementPKSurrogate primary key
titleVARCHAR(180)NOT NULLEvent name on the public listing
descriptionTEXTNULLFull details of the event
event_dateDATETIMENOT NULLDate and time of the event
venue_idINTFK -> VENUESWhere the event is held (normalised venue)
deleted_atDATETIMENULLSoft delete: archived events keep their history
max_participantsINTNOT NULL, >= 1Slot limit; registration is blocked once reached
(index)INDEX(event_date)indexOrdering of the public listing

REGISTRATIONS

FieldTypeKey / constraintDescription
registration_idINT, auto incrementPKSurrogate primary key
user_idINTFK -> USERSParticipant who registered
event_idINTFK -> EVENTSEvent being registered for
registration_dateDATETIMEdefault nowTimestamp when the registration was saved
statusENUM(confirmed, waitlisted, cancelled)default confirmedRegistration state
(composite)UNIQUE(event_id, user_id)indexDatabase-level duplicate prevention
(indexes)INDEX(event_id,status) / (user_id,status) / (status,registration_date)indexCapacity counts, participant filters, FIFO waitlist promotion
Duplicate rule: a composite UNIQUE index on REGISTRATIONS(event_id, user_id) blocks a second registration from the same email for the same event.
Capacity rule: confirmed registrations may never exceed EVENTS.max_participants.

3.2 Exception paths

ConditionSystem response
Email already registered for the eventHTTP 409 + views/events/duplicate.ejs — “You are already registered”
Missing field or invalid emailHTTP 422 + form redisplayed with the error list
Two participants submit the last slot at the same timeThe second transaction re-counts inside a row lock and returns the “Event full” page — no overbooking
A confirmed participant cancelsSlot is freed and the earliest waitlisted registration is promoted to confirmed

7. Business Rules

#RuleEnforcement
BR-1Registration is only allowed while confirmed < max_participantsApplication check, re-counted inside a transaction with a row lock
BR-2One registration per email address per eventUNIQUE(event_id, user_id) index + application check (HTTP 409)
BR-3Full name and a valid email are requiredmiddlewares/validate.js (server) + public/js/main.js (client)
BR-4Passwords are hashed, never stored in plain textbcrypt hook in models/User.js
BR-5Only admins may create, edit or delete eventsrequireAdmin middleware → HTTP 403
BR-6Capacity cannot drop below the confirmed head-counteventController.update validation
BR-7Cancelling a confirmed slot promotes the earliest waitlisted personregistrationController.cancel and adminController.updateStatus
BR-8Attendance list contains confirmed registrations onlyadminController.attendance (SQL filter on status)
